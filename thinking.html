Short technical notes on the engineering decisions behind reliable data platforms. These are working ideas, not commandments.

01 · DATA RELIABILITY · 6 MIN

What schema drift actually breaks

A changed column is visible. Its blast radius usually is not.

Schema drift is often treated as a local data-quality problem: a field disappears, a type changes, or a nested structure moves. But the useful engineering question is not only “what changed?” It is “what depends on what changed?”

That dependency chain can reach transformations, tests, dashboards, ML features and operational reports. The platform therefore needs two abilities: change detection and impact reasoning. Detection without lineage tells you there is a fire. Impact reasoning tells you which rooms are connected.

My Iceberg research explored this as a graph problem: represent the lakehouse hierarchy and propagate the impact of a metadata change downstream. The practical lesson is simple: schema governance should be designed around dependency, not just comparison.

02 · PLATFORM ENGINEERING · 5 MIN

Infrastructure as Code is a data engineering skill

A pipeline cannot be more reliable than the environment it depends on.

Data engineering discussions often stop at Python, SQL, orchestration and modelling. Production systems do not. They depend on networks, identity, compute, secrets, storage and deployment paths.

Infrastructure as Code closes an important gap: it turns platform assumptions into versioned, reviewable configuration. A bucket, role or task definition becomes part of the system rather than a one-off setup step someone performed months ago.

For data engineers, this creates a better operating model. Environments can be recreated, changes can be reviewed, and architecture becomes easier to reason about as code rather than institutional memory.

03 · ANALYTICS ENGINEERING · 4 MIN

dbt is powerful. It is not your entire platform.

Transformation is one layer of reliability, not the whole thing.

dbt brings structure to SQL transformation: modular models, tests, documentation and lineage. That is valuable. But production reliability also depends on ingestion contracts, orchestration, compute, secrets, deployment, monitoring and failure recovery.

The useful mental model is to treat dbt as a transformation product inside a broader platform. When that boundary is clear, responsibilities become clearer too: orchestration decides when work runs, infrastructure decides where it runs, and dbt defines how analytical data is transformed and tested.
